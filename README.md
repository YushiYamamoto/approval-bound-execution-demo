# 承認内容に束縛した、1回の実行開始ゲート

**この記事用に新規作成した、架空データのローカル再現実験です。実運用での導入実績や、外部操作の完全な exactly-once を示すコードではありません。** Python 標準ライブラリと SQLite だけを使い、ネット通信・LLM・外部 API は呼びません。

単純な `approved = True` だけでは、その後に本文が変わったり、同じ処理が再実行されたりすることを防げません。このデモは「何を承認したか」と「同じ承認で実行開始してよいか」を別々に確認します。

## 実行

Python 3.10 以上が必要です。外部パッケージの追加は不要です。

```bash
git clone https://github.com/YushiYamamoto/approval-bound-execution-demo.git
cd approval-bound-execution-demo
python3 -m unittest -v
python3 demo.py
```

テスト・デモは一時ディレクトリを使い、終了時に消します。本番の DB や設定は読みません。

## 公開 API

```python
from gate import Request, approve, execute

request = Request("send_message", "demo@example.invalid", "架空のお知らせ")
approval_id = approve("demo.sqlite3", request, ttl_seconds=30)
receipt = execute("demo.sqlite3", approval_id, request,
                  lambda approved_request: "local-receipt")
```

- `Request(action, destination, body)` は `frozen=True` の dataclass。`effect` へも検証した同じ値を渡し、可変のファイルを再読込しません。
- `approve(...) -> approval_id` は、**別途、人の承認を確認した trusted runner だけが呼ぶ**想定です。この関数自体が承認者の本人認証を行うわけではありません。
- `execute(..., effect, clock=...) -> receipt` は実行開始権を取得してから、trusted runner の `effect` を一度呼びます。`effect` の意味や実装が正しいことは別途必要です。
- `clock` は trusted runner が決める時計関数です。省略時は実時計の Unix 時刻を `int(time.time())` で整数秒にします。テストでは `clock=lambda: 100` のように注入します。公開クライアントが時計関数や時刻を自由に与える想定ではありません。実運用では信用できる時計と巻き戻り時の扱いが必要です。
- `approve` は書き込みロック取得後に時計を読み、承認時刻と有効期限を決めます。`execute` も **`BEGIN IMMEDIATE` が返った後**に時計を読み、その時刻で期限照合と条件付き更新を行います。呼出し前の固定時刻を、ロック待ちの後まで使い回しません。
- 入力は型・空値・UTF-8 でのサイズを確認します。action は英小文字で始まる英小文字・数字・`_` の最大 64 バイト、宛先は最大 256 バイト、本文は最大 65,536 バイト。TTL は整数 1〜86,400 秒です。対応可能な action、宛先、内容の**業務上の許可ポリシーは別途**必要です。

## 束縛する値と取得手順

`schema_version`・`action`・`destination`・`body` をキー順固定・空白なし・`ensure_ascii=False` の JSON へ変換し、UTF-8 の SHA-256 を保存します。文字列の Unicode 正規化・改行変換・trim は行いません。承認 ID は `uuid4().hex` で生成します。ハッシュは本人認証や秘密鍵の署名を代替しません。

SQLite には本文・宛先の平文を保存せず、全体ハッシュ・action 名・宛先ハッシュ・有効期限・状態・結果識別子を保存します。**ハッシュからの推測が不可能という意味ではありません**。辞書攻撃可能な短い値や DB 本体も、必要なアクセス制御の対象です。

1. `BEGIN IMMEDIATE` で書き込み競合を直列化する。
2. ロック取得後に trusted runner の `clock()` を読み、承認 ID、状態、期限、action、宛先ハッシュ、全体ハッシュを確認する。`now >= expires_at` は失効扱い。
3. `state='APPROVED'` 等の条件を付けて `RUNNING` へ更新する。
4. 監査イベントと共に **commit してから** effect を呼ぶ。
5. 空でない結果識別子を受け取り、`SUCCEEDED` を記録する。

```text
APPROVED ── 内容一致・期限内・開始権取得 ──> RUNNING ── receipt ──> SUCCEEDED
                                               └─ 例外/空receipt ──> UNKNOWN
```

`RUNNING`・`SUCCEEDED`・`UNKNOWN` では再開始しません。内容差替えや期限切れは effect を呼ばず拒否します。新しい内容を実行したい場合は、人がその内容を確認する別の承認が必要です。

監査イベントは承認 ID・状態・固定の reason code・trusted runner が測定した観測時刻だけです。本文・宛先・例外メッセージは書きません。終了イベントの時刻もこのデモでは開始権の照合に使った同じ時刻であり、処理の実所要時間を測定した値ではありません。

## 比較実験

`demo.py` は、同じ架空条件で単純な承認フラグとゲートを比較します。出力は内容や宛先を含まない JSON です。

| 条件 | 単純フラグの模擬受理件数 | ゲートの模擬受理件数 | ゲート側の結果 |
|---|---:|---:|---|
| 承認後に本文を差替え | 1 | 0 | `CONTENT_MISMATCH` |
| 同じ承認で2回呼ぶ | 2 | 1 | 2回目 `ALREADY_STARTED` |
| 模擬送信先が受理後にタイムアウト | 2 | 1 | `UNKNOWN`、再開始は `ALREADY_STARTED` |

最後の行は、模擬送信先のメモリ上のリストへ追加した**後**に `TimeoutError` を返します。実在サービスへの送信・ネットワーク障害を再現した結果ではありません。

`test_gate.py` は、通常/Unicode の成功、本文・宛先・行為の差替え、期限境界、未承認、再実行、別の SQLite 接続からの実際の同時競合、受理後のタイムアウト、空の結果識別子、中断、実行成功後の DB 記録失敗、入力検証、ログへの値の漏出を検証します。

### 18テスト通過後に見つかった、時計を読む時点の不備

初版は呼出し側が `now` を固定して渡していました。18テストは通りましたが、独立レビューで「`BEGIN IMMEDIATE` のロック待ちの間に期限が過ぎても、古い時刻で照合する」という不備が見つかりました。これは今回のローカル検証コードの不備であり、実運用システムの障害事例ではありません。

現行版では固定値の `now` API を除き、ロック取得後に trusted runner の時計を読みます。回帰テスト `test_expiry_is_measured_after_real_sqlite_writer_lock_wait` は、別の実 SQLite 接続で書き込みロックを保持し、`execute` が `BEGIN IMMEDIATE` に到達したことをイベントで確認します。その後、注入時計を100から132へ進め、期限130を超えてからロックを解放します。**effect の呼び出しは0回、結果は `EXPIRED`、時計を読んだ値は132**であることを確認します。時計はテスト用の論理時刻であり、実際に32秒待った結果ではありません。

## 残る限界と運用前に必要なこと

- **DB と runner を信頼する前提です。** 提案側の AI が DB を書けない境界が必要です。同一 UID で動く AI が DB や runner を直接書き換えられる場合、このデモだけでは防げません。OS ユーザー、実行環境、書込み権限、呼び出せる経路等の分離は未実装です。
- **承認者認証、承認 UI、秘密情報管理は未実装です。** 誰が承認したかを立証せず、`approve` を呼べること自体を権限としています。承認 ID を秘密にするだけでは、人の承認を保証できません。
- **1承認 ID あたり、通常の単一 DB 履歴で開始権を1回に絞る設計です。** 別の承認 ID を発行すれば、同じ内容でも再び実行できます。業務キーを通じた重複検出は未実装です。DB の復元・複製、履歴巻き戻し、マルチリージョン、SQLite 不適合ファイルシステム等は対象外です。
- **完全な exactly-once ではありません。** `RUNNING` の commit 後、effect 前に停止すれば、実際は未実行でも再開始を拒否します。受理後に応答を失えば、送信先とローカル DB の状態が食い違います。effect 成功後に DB 記録が失敗しても同様です。可用性より、無条件の再送による重複を避けます。
- **`KeyboardInterrupt` 等では `RUNNING` が残ります。** `Exception` として処理しない中断、プロセス強制終了、DB 障害等でも再開始は禁止です。「実行されなかった」と推測して状態を戻してはいけません。実運用で復旧するには送信先の受領照合、人の判断、操作に応じた冪等性キー等を別途設計します。
- **receipt の正当性は effect 側の責任です。** 空でない文字列を検査するだけで、送信先の実受領や業務成功を立証しません。期限はロック取得後の開始権照合時に判定します。commit や effect 呼出しまでの遅延、callback 内の送信時刻を拘束せず、外部送信が期限前に実際に始まることを保証しません。開始後の処理を自動で取消すものでもありません。
- Python の frozen dataclass は通常の代入ミスを防ぐ仕組みで、悪意ある同一プロセスの Python コードに対する隔離境界ではありません。callback 自体や別の送信経路が悪意を持つ場合も防げません。

この実験から言えるのは、示した条件の下で、内容差替えを拒否し、同じ承認 ID に対する開始の競合・再開始を止められたことまでです。実環境の本人認証・権限分離・外部操作の冪等性を検証したことにはなりません。
